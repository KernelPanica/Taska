# Taska — roadmap разработки с checkpoints

## 1. Цель перезапуска

С нуля собрать Taska как рабочий таск-трекер, в который можно перенести текущие процессы из Taiga, а затем отказаться от ручного roadmap в Google Sheets за счёт встроенных Gantt-представления, истории изменений и метрик.

Этот roadmap **не включает** вики, документы, Google Drive, Unit Wiki и любые связанные с ними интеграции.

## 2. Принцип разработки

Каждый этап заканчивается checkpoint — состоянием продукта, которое можно показать команде и проверить по пользовательскому сценарию.

Правила прохождения checkpoint:

- реализованы все обязательные пункты этапа;
- основной сценарий проходит без ручного вмешательства в базу;
- данные сохраняются после перезапуска приложения;
- нет блокирующих ошибок и потери данных;
- выполнена короткая демонстрация команде;
- замечания после демонстрации либо исправлены, либо заведены отдельными задачами;
- следующий этап не начинается, пока не согласован результат текущего.

## 3. Границы первой версии

### В MVP входят

- пользователи и проекты;
- типы задач;
- создание, просмотр, редактирование и удаление задач;
- kanban-доска;
- статусы и переходы между ними;
- исполнители, заказчик и наблюдатели;
- сроки, оценка сложности, теги и приоритет;
- Markdown-описание и комментарии;
- вложения;
- связи и произвольная вложенность задач;
- история действий;
- фильтры и доски из нескольких проектов;
- импорт данных из Taiga.

### После MVP

- swimlanes;
- Gantt/roadmap;
- dashboards и продуктовые метрики;
- вероятностный прогноз сроков;
- календарные интеграции;
- расширенная кастомизация интерфейса.

### Не входят

- вики и редактор документов;
- Google Drive и Google Docs;
- whiteboard;
- встроенные звонки;
- timesheet;
- отдельная система goals;
- обязательный progress bar в первой версии.

# Этап 0. Зафиксировать продукт и технический фундамент

## Задачи

- Описать основные сущности: User, Project, Board, Issue, IssueType, Status, Tag, Comment, Attachment, Relation, Activity.
- Зафиксировать права минимум для ролей: администратор, участник проекта, наблюдатель.
- Определить жизненный цикл задачи и три категории статусов:
  - очередь;
  - активный;
  - завершённый.
- Решить, какие поля обязательны при создании задачи, а какие можно заполнить позже.
- Спроектировать API и схему базы так, чтобы задачи, статусы и типы не были жёстко привязаны к одному UI.
- Подготовить локальный запуск одной командой и отдельную тестовую конфигурацию.
- Добавить миграции БД, базовое логирование ошибок и автоматические проверки форматирования/тестов.
- Создать тестовый проект с демонстрационными пользователями и задачами.

## Checkpoint 0 — «Пустой, но устойчивый фундамент»

Checkpoint пройден, если:

- новый разработчик запускает проект по README без ручной настройки базы;
- миграции применяются на чистой БД и повторный запуск ничего не ломает;
- можно войти под тестовым пользователем;
- API отдаёт тестовый проект и пустой список задач;
- ошибки API имеют единый формат;
- основные сущности и спорные решения записаны в коротком ADR/техническом описании.

## Что показать команде

Чистая установка → вход → открытие тестового проекта → пустая доска.

# Этап 1. Базовая задача и её карточка

## Задачи

- Создание задачи с уникальным читаемым ID внутри проекта, например `TASKA-123`.
- Отображение в верхней части карточки:
  - ID;
  - названия;
  - текущего статуса;
  - типа задачи.
- Редактирование названия и описания через явную кнопку/иконку, а не скрытое действие.
- Markdown в описании с безопасным предпросмотром.
- Базовые типы: task, bug, request, story, epic.
- Возможность создавать пользовательские типы и менять тип существующей задачи.
- Для типа: название, цвет и иконка.
- Целочисленная оценка сложности.
- Приоритет.
- Теги: создание, добавление и удаление.
- Дата начала и дата окончания.
- Удаление задачи с подтверждением.

## Checkpoint 1 — «Задачей уже можно пользоваться»

Checkpoint пройден, если пользователь может:

1. Создать задачу.
2. Открыть её кликом по любой свободной части карточки.
3. Изменить название, Markdown-описание, тип, статус, оценку, приоритет, теги и даты.
4. Обновить страницу и увидеть сохранённые значения.
5. Удалить задачу, подтвердив действие.

Дополнительно:

- ID не переиспользуются после удаления;
- дата окончания не может быть раньше даты начала без явного предупреждения;
- некорректный Markdown не ломает страницу;
- карточка с длинным названием и описанием остаётся пригодной для использования.

## Что показать команде

Создание bug → заполнение полей → редактирование → обновление страницы → удаление.

# Этап 2. Люди и коммуникация внутри задачи

## Задачи

- Назначение одного или нескольких исполнителей.
- Кнопка «Назначить на себя».
- Поле «Заказчик» с одним или несколькими пользователями.
- Поле «Наблюдатели».
- Один человек может одновременно быть исполнителем, заказчиком и наблюдателем.
- Поиск пользователей при назначении.
- Добавление и удаление участников без потери ранее выбранных пользователей после обновления списка.
- Профиль пользователя с именем и email.
- Комментарии: создание, редактирование собственного комментария и удаление согласно правам.
- Подписка наблюдателей на изменения задачи.
- Почтовые уведомления сделать отключаемыми; при отсутствии готовой почтовой инфраструктуры сначала реализовать очередь событий и тестовый адаптер.

## Checkpoint 2 — «Команда работает в карточке»

Checkpoint пройден, если:

- PM назначает двух исполнителей, заказчика и наблюдателя;
- исполнитель одним действием назначает задачу на себя;
- участники оставляют комментарии;
- наблюдатель получает событие об изменении статуса и новом комментарии;
- удаление участника из задачи не удаляет его профиль и не портит историю;
- права проверяются сервером, а не только скрытием кнопок в интерфейсе.

## Что показать команде

PM создаёт задачу → назначает людей → исполнитель комментирует → меняется статус → наблюдатель получает уведомление.

# Этап 3. Kanban-доска и статусная модель

## Задачи

- Доска с колонками, соответствующими статусам.
- Настраиваемые статусы внутри проекта.
- Для каждого статуса обязательна категория: очередь, активный или завершённый.
- Смена статуса:
  - drag-and-drop карточки;
  - через явный контрол в карточке задачи.
- Перетаскивание за всю карточку, кроме интерактивных элементов.
- Быстрое редактирование названия колонки для пользователей с правами.
- На карточке доски показывать минимум:
  - ID;
  - название;
  - тип;
  - исполнителей;
  - приоритет;
  - теги;
  - срок окончания;
  - признак просрочки.
- Переход по тегу, исполнителю или связанной сущности без необходимости попадать точно в текст названия.
- Стабильный порядок карточек внутри колонки.

## Checkpoint 3 — «Полноценная рабочая доска»

Checkpoint пройден, если:

- пользователь видит состояние проекта без открытия каждой задачи;
- карточка перетаскивается между статусами и сохраняет новое положение;
- статус можно поменять внутри карточки задачи;
- просроченная задача заметна на доске;
- одновременное изменение одной карточки двумя пользователями не приводит к тихой потере данных;
- доска остаётся пригодной для работы минимум со 100 карточками.

## Что показать команде

Рабочий спринт из 15–20 задач: создание → назначение → перенос по статусам → завершение.

# Этап 4. Связи, вложенность и прогресс

## Задачи

- Единый интерфейс добавления связей.
- Типы связей:
  - обычная связь;
  - блокирует / заблокирована;
  - родитель / дочерняя задача.
- Возможность поменять тип существующей связи без удаления и повторного создания.
- Возможность удалить связь.
- В карточке связанной задачи показывать:
  - ID и название;
  - проект;
  - статус;
  - исполнителя;
  - тип связи;
  - теги/labels.
- Клик по связи открывает соответствующую задачу.
- Произвольная глубина вложенности без жёсткой привязки уровней к issue type.
- Защита от циклов: задача не может стать собственным предком.
- Расчёт прогресса:
  - epic/родительская задача — по завершённым дочерним задачам;
  - story — опционально по checklist;
  - bug/request — только «готово / не готово»;
  - отсутствие progress bar допустимо, если источник прогресса не определён.

## Checkpoint 4 — «Можно управлять зависимостями»

Checkpoint пройден, если:

- создаётся дерево минимум из четырёх уровней;
- родитель показывает дочерние задачи и рассчитанный прогресс;
- блокирующая связь видна с обеих сторон;
- тип связи меняется одним действием;
- система запрещает циклическую вложенность;
- удаление связи не удаляет сами задачи.

## Что показать команде

Epic → story → task → subtask, параллельно одна задача блокирует другую; завершение дочерних задач меняет прогресс родителя.

# Этап 5. Вложения и полная история действий

## Задачи

- Загрузка, скачивание и удаление вложений согласно правам.
- Ограничения размера и допустимых типов файлов.
- Безопасные имена файлов и хранение вне публично исполняемого каталога.
- Ссылка на вложение из Markdown-описания и комментария.
- Вкладки «Комментарии» и «Действия».
- Неизменяемый журнал действий минимум для:
  - создания и удаления задачи;
  - изменения названия и описания;
  - изменения статуса, типа, приоритета и оценки;
  - назначения и снятия пользователей;
  - изменения дат;
  - добавления, изменения и удаления связей;
  - добавления и удаления вложений.
- Для события хранить автора, время, тип действия, старое и новое значение там, где это уместно.

## Checkpoint 5 — «Данным можно доверять»

Checkpoint пройден, если:

- файл можно приложить отдельно и вставить ссылкой в Markdown;
- запрещённый тип или слишком большой файл отклоняется понятной ошибкой;
- история показывает, кто, когда и что изменил;
- обычный пользователь не может переписать или удалить аудит;
- из истории можно восстановить последовательность смены статусов для будущих метрик.

## Что показать команде

Загрузка вложения → вставка в описание → несколько изменений задачи → проверка полной хронологии во вкладке «Действия».

# Этап 6. Проекты, составные доски и фильтры

## Задачи

- Несколько независимых проектов/пространств.
- Одна или несколько досок внутри проекта.
- Отдельная доска может показывать задачи из нескольких проектов.
- Глобальные сохранённые фильтры, доступные другим пользователям согласно правам.
- Визуальный конструктор фильтра как минимум по:
  - проекту;
  - статусу и категории статуса;
  - типу задачи;
  - исполнителю;
  - заказчику;
  - тегу;
  - приоритету;
  - диапазону дат;
  - просрочке.
- Полнотекстовый поиск по ID, названию и описанию.
- Swimlanes с группировкой хотя бы по проекту, исполнителю, типу и родительской задаче.
- Боковая навигация между проектами, досками и сохранёнными фильтрами.

## Checkpoint 6 — «Одна доска для кросс-функциональной команды»

Checkpoint пройден, если lead может:

1. Создать доску из задач нескольких проектов.
2. Отфильтровать только задачи своей команды.
3. Сохранить фильтр для всех участников.
4. Сгруппировать результат по исполнителям или родительским задачам.
5. Открыть найденную задачу по ID или названию.

## Что показать команде

Три проекта → общая доска feature team → фильтр по специалистам → swimlanes по исполнителям.

# Этап 7. Готовность к миграции из Taiga

## Задачи

- Составить точное соответствие полей Taiga и Taska.
- Импортировать как минимум:
  - проекты;
  - пользователей и участников;
  - задачи и их исходные ID;
  - типы;
  - статусы;
  - описания;
  - исполнителей;
  - теги;
  - сроки;
  - комментарии;
  - вложения;
  - связи и родительские отношения;
  - историю, если она доступна в экспорте/API.
- Импорт должен быть повторяемым и не создавать дубликаты.
- Сформировать отчёт: что импортировано, пропущено и преобразовано с потерями.
- Провести пробную миграцию на копии реальных данных.
- Подготовить план отката и период read-only для старой системы.

## Checkpoint 7 — «Можно переезжать»

Checkpoint пройден, если:

- тестовый экспорт Taiga импортируется без ручной правки БД;
- повторный импорт не дублирует сущности;
- выборочная сверка минимум 30 задач не выявляет потери обязательных полей;
- количество проектов, задач, комментариев и вложений сверено автоматически;
- все расхождения перечислены в отчёте;
- команда проводит один реальный рабочий цикл в Taska без блокирующих проблем.

## Что показать команде

Импорт копии рабочего проекта → автоматический отчёт → выборочное сравнение задач в Taiga и Taska.

# MVP Gate — решение о переходе

Переход с Taiga возможен только после checkpoints 0–7.

Критерии MVP Gate:

- основные пользовательские сценарии проходят без обращения к разработчику;
- нет известных ошибок с потерей или повреждением данных;
- права доступа проверены минимум для администратора, участника и наблюдателя;
- выполнены резервное копирование и тестовое восстановление;
- импорт проверен на копии реальных данных;
- согласовано окно финальной миграции;
- назначен период, в который Taiga остаётся доступной только для сверки.

# Этап 8. Gantt и встроенный roadmap

## Задачи

- Gantt как альтернативное представление тех же задач, а не отдельное хранилище.
- Строки с краткой информацией о задаче.
- Отображение даты начала, окончания и длительности.
- Раскрытие и сворачивание дочерних задач.
- Отображение блокирующих зависимостей.
- Группировка по проекту, исполнителю, типу, тегу и родительской задаче.
- Изменение сроков на диаграмме с записью в обычную историю задачи.
- Подсветка просрочек и конфликтов зависимостей.

## Checkpoint 8 — «Google Sheets больше не нужен для roadmap»

Checkpoint пройден, если PM может построить roadmap из существующих задач, раскрыть декомпозицию, увидеть зависимости и изменить срок без двойного ввода данных.

# Этап 9. Dashboards и метрики потока

## Задачи

- Фильтр периода и тех же разрезов, что используются на доске.
- Базовые показатели:
  - создано задач;
  - завершено задач;
  - незавершённый объём;
  - распределение по ответственным;
  - распределение по типам, приоритетам и размерам;
  - число просроченных задач.
- Расчёт времени перехода между любыми двумя выбранными статусами.
- Lead time и cycle time с явно зафиксированными определениями.
- Перцентили сроков выполнения, включая 50-й, 85-й и 95-й.
- График: «85% подобных задач завершаются не дольше N дней».
- Разрезы по проекту, типу, исполнителю, размеру и тегу.
- Исключение или отдельная маркировка задач с неполной историей после миграции.

## Checkpoint 9 — «Система отвечает на вопросы о сроках»

Checkpoint пройден, если PM выбирает период, тип задач и два статуса и получает воспроизводимый расчёт времени перехода, а также 85-й перцентиль полного срока выполнения.

Важно: сначала система показывает статистический ориентир, а не обещает “предсказать точную дату” для отдельной задачи.

# Этап 10. Стабилизация и эксплуатация

## Задачи

- Автоматические резервные копии и проверенное восстановление.
- Мониторинг ошибок, доступности, очередей уведомлений и свободного места.
- Ограничение частоты запросов и защита загрузки файлов.
- Экспорт данных проекта в переносимом формате.
- Нагрузочные проверки на реальном ожидаемом объёме данных.
- Проверка доступности интерфейса с клавиатуры и на небольших экранах.
- Документация администратора и короткая инструкция пользователя.
- Процедура обновления без потери данных.

## Checkpoint 10 — «Taska готова жить без автора рядом»

Checkpoint пройден, если администратор, не участвовавший в разработке, может развернуть обновление, восстановить резервную копию и разобраться с типовой ошибкой по документации.

# Сквозные требования для каждого этапа

## Надёжность

- Сервер валидирует все изменения независимо от UI.
- Миграции БД имеют проверяемый путь вперёд; для рискованных изменений предусмотрен откат из резервной копии.
- Критические операции идемпотентны там, где возможны повторы запроса.
- Конкурирующие изменения не должны молча затирать данные.

## Безопасность

- Проверка прав выполняется для каждого чтения и изменения сущности.
- Markdown очищается от опасного HTML/скриптов.
- Вложения не исполняются сервером и недоступны в обход проверки прав.
- Пароли не хранятся в открытом виде; сессии можно отозвать.
- Секреты не попадают в репозиторий и логи.

## UX

- Кликабельная область карточки достаточно большая.
- Редактируемые элементы имеют явные affordances: кнопка, иконка или подпись.
- Частые операции выполняются без лишних модальных окон.
- Ошибка объясняет, что произошло и что можно сделать.
- После сохранения пользователь видит актуальное состояние без ручной перезагрузки.

## Тестирование

- Unit-тесты для бизнес-правил.
- Интеграционные тесты API и БД.
- E2E-тесты для демонстрационного сценария каждого checkpoint.
- Регрессионный набор для создания, изменения, перемещения, связывания и импорта задач.

# Первый практический цикл

Чтобы не расползтись в бесконечную разработку, первый цикл лучше ограничить checkpoints 0–3:

1. Зафиксировать модель и поднять чистый каркас.
2. Сделать полноценную карточку задачи.
3. Добавить людей и комментарии.
4. Собрать рабочую kanban-доску.
5. Провести демонстрацию на 15–20 реальных задачах.
6. Только после обратной связи переходить к связям, истории и миграции.

До прохождения Checkpoint 3 не начинать Gantt, dashboards, сложные метрики, календарные интеграции и декоративную кастомизацию.
