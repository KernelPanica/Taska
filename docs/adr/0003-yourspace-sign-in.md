# 0003. Вход только аккаунтом YourSpace

- Статус: принято (2026-11-16); протокол зафиксирован в [0009](0009-catalog-people.md): провайдер — сервис YourSpace, подпись id_token проверяется, роль приходит в `yourspace_role`
- Требования: R-2.1, R-3.2, R-2.40 (строка «Вход»), R-0.4; YS-01 «Аккаунт YourSpace: вход, привязка Google и восстановление пароля»; YT-01, п. 2

## Уточнение 2026-11-23: единый вход и регистрация при входе

На странице YourTask одна кнопка «Войти через YourSpace». Способ подтверждения личности (пароль, связанный Google, MFA) выбирается на стороне YourSpace. У YourTask нет отдельного входа по паролю и отдельной формы регистрации.

Успешный первый OIDC-вход аккаунта, отсутствующего в YourTask, автоматически создаёт локальную проекцию по постоянному `sub`. Если каталог уже синхронизировал человека, используется существующая запись. Повторный вход не создаёт дубль. Непроверенный или поддельный ответ провайдера не создаёт аккаунт; деактивированные пользователи не возвращаются через регистрацию. Действующие правила доступа к пространствам сохраняются.

При переключении с публичного демо на настоящий YourSpace включается профиль `production`, отключаются заглушки и начальное создание тестовых данных, отзываются сессии прежнего тестового провайдера. Существующие тикеты, люди и история остаются в базе; аккаунты разных провайдеров не связываются по email автоматически.

## Контекст

Вход — аккаунтом YourSpace: по логину и паролю или через привязанный Google. YourTask своих паролей не хранит. Суперадмину и админам вторая проверка входа обязательна. Сессии можно отозвать.

По R-2.1 аккаунты YourSpace **хранятся на стороне YourWiki**: YourTask и YourDash пускают по тому же аккаунту. Регистрация, привязка Google, восстановление пароля, коды восстановления второй проверки и деактивация — всё на стороне YourWiki (YS-01, YS-02).
YS-01 требует описать в техдоке YourWiki, как продукт проверяет аккаунт YourSpace. На 16.11.2026 в YourWiki есть только собственный вход по cookie (`POST /api/auth/login`); входа для других продуктов и второй проверки там пока нет. Протокол поэтому не зафиксирован.

## Решение

1. **Граница** — интерфейс `IdentityProvider` (`apps/api/src/auth/provider.ts`): «адрес входа» + «обмен одноразового кода на личность»
   (`subject`, `email`, `name`, `locale`, способ входа, была ли вторая проверка). Форма повторяет OpenID Connect authorization code + PKCE (S256), state и nonce.
2. **Две реализации:**
   - `DevYourSpace` — заглушка для разработки и тестов, маршруты `/dev/yourspace/*`: логин/пароль, «вход через Google» (выбор привязанного аккаунта), вторая проверка кодом, короткая SSO-сессия для повторной проверки. Тестовые аккаунты — `apps/api/src/testing/accounts.ts`.
   - `OidcYourSpace` — OIDC-адаптер настоящего YourSpace. Код обменивается на token endpoint по TLS с аутентификацией клиента. Подпись RS256 проверяется ключами JWKS; также проверяются `iss`, `aud`, `exp`, `nonce`.
3. **Пользователь YourTask** — проекция аккаунта по `yourspace_subject`; создаётся при первом входе. В таблице `users` нет полей для паролей и кодов (проверяется тестом).
4. **Вторая проверка суперадмина.** Роль `superadmin` (глоссарий, раздел 1) — в YourTask (`YOURTASK_SUPERADMIN_EMAILS` или тестовые данные). Если суперадмин вошёл без второй проверки, YourTask один раз отправляет его обратно в YourSpace с требованием второй проверки (step-up); если её снова нет — вход отклоняется (`mfa_required`). Эндпоинты суперадмина дополнительно требуют `mfa` у текущей сессии. Админ пространства (R-2.20) появится с правами в YT-08 и получит то же требование.
5. **Сессии** — случайный токен в HttpOnly-cookie `yourtask_session` (SameSite=Lax), в БД — только HMAC токена. Изменяющие запросы требуют заголовок `x-yourtask-csrf`. Пользователь видит свои сессии и отзывает любую или все остальные; админ отзывает все сессии пользователя. Отзыв действует немедленно.

## Предположения — сверить с YS-01

| Что                        | Принято сейчас                                                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Протокол                   | OIDC authorization code + PKCE                                                                                                |
| Выбор входа через Google   | параметр `yourspace_method=google`                                                                                            |
| Запрос второй проверки     | `acr_values=mfa`, `prompt=login`                                                                                              |
| Признак второй проверки    | `amr` ∋ `mfa`/`otp`/`hwk`/`swk`/`totp` или `acr=mfa`                                                                          |
| Признак входа через Google | `amr` ∋ `google`/`fed`                                                                                                        |
| Кто назначает суперадмина  | YourTask (`YOURTASK_SUPERADMIN_EMAILS`); по R-2.20 роли общие для трёх продуктов — возможно, роль будет приходить из YourWiki |
| Провайдер                  | YourWiki (R-2.1); адрес и способ проверки — из техдоки YS-01                                                                  |

Когда протокол YS-01 будет утверждён, меняется только `oidc-provider.ts` (и при необходимости заглушка), остальной код от него не зависит.

## Что из R-3.2 сознательно отложено

По карточкам эти пункты сдаются в YT-27 «Базовая безопасность»: журнал безопасности, выход по неактивности (тайм-аут сессии), HTTPS/HSTS, шифрование копий, проверка зависимостей в каждой сборке. Ограничение частоты запросов (R-3.2) тоже стоит закрыть там. Деактивация участника, закрывающая вход и сессии, — YT-03 (вместе с каталогом YS-02).

## Последствия

- Восстановление пароля и привязка Google — целиком на стороне YourSpace.
- Если YourSpace не умеет вторую проверку, админы не смогут войти — это осознанно (требование обязательное).
