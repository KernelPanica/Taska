# 0010. Конструктор типов, полей, шаблонов и оценок

- Статус: принято, 2026-11-17
- Требования: R-2.5 (сущности «Тип», «Поле»), R-2.7 (типы и шаблоны), R-2.12 (свёртки — только настройки), R-2.26 (оценка и конвертер); карточка YT-04. Смежные: YT-05 (схемы статусов), YT-06 (тикеты), YT-09 (иерархия), YT-10 (свёртки), YT-15 (TQL), YT-25 («Отсутствие»)

## Контекст

Структуру тикетов команда меняет сама, без разработчика. Нужны:

- типы: имя, цвет, иконка, поля, шаблоны, свёртки, ограничители подчинения;
- поля семи видов с латинским системным именем для TQL;
- шаблоны, по нескольку на тип;
- шкалы оценки с конвертером на пространство.

Тикетов, иерархии и свёрток ещё нет, они появятся в YT-06, YT-09 и YT-10. Поэтому YT-04 делает модель, API и интерфейс настройки, а критерии про тикеты показывает на предпросмотре шаблона и в API свёртки оценок.

## Решение

**Где живут типы.** Типы, поля, шаблоны и шкалы общие для установки, как измерения (ADR 0008). Так стори в «Core» и в «Производстве» — один и тот же тип, и TQL, доски и свёртки видят одинаковые поля. По пространству настраивается то, что требования прямо называют «на пространство»:

- конвертер оценок;
- включение ограничителей подчинения.

Схему статусов «на тип в пространстве» добавит YT-05.

**Типы** — таблица `ticket_types`:

- имя уникально, системное имя (`key`) латиницей;
- цвет `#RRGGBB`;
- иконка — имя из фиксированного набора `TYPE_ICONS`, рисует клиент;
- поля упорядочены (`ticket_type_fields.position`), в этом порядке они идут в карточке.

Свёртки — JSON в `rollups`: `status`, `progress` (`children` | `checklist` | `both` | `status` | `none`), `progressByEstimate`, `dates`, `estimates`. Сейчас это только хранение, считать будет YT-10.

Ограничитель подчинения — `ticket_type_parents`: какие типы могут быть родителем; пусто — любой. Он действует только в пространствах с `spaces.enforce_subordination = 1`, по умолчанию выключено (R-2.7). Проверка — `canBeParent()` и `GET /api/v1/ticket-types/subordination`; YT-09 вызовет её при добавлении родителя.

**Поля** — таблица `ticket_fields`, виды: текст, число, дата, список, человек, шкала оценки, измерение.

- Системное имя — `^[a-z][a-z0-9_]{1,39}$`, не из списка встроенных атрибутов TQL (`RESERVED_FIELD_KEYS`: `status`, `type`, `parent`…). Если не задано, получается транслитом из названия («Платформа релиза» → `platforma_reliza`).
- Вид, системное имя, шкала и измерение после создания не меняются: на них будут опираться значения тикетов и запросы.
- Варианты списка меняются; id варианта с тем же текстом сохраняется.
- Поле, которое использует тип, удалить нельзя: сначала его убирают из типа.

**Шаблоны** — таблица `ticket_templates`: название (уникально в типе), структура описания в Markdown, чеклист и значения полей по системному имени.

- Значения проверяются по виду поля и набору полей типа: вариант списка, активный человек, значение шкалы, группа или вариант измерения.
- Если поле убрали из типа, его значение в шаблоне скрывается, но не стирается — как у тикетов (R-2.7).
- Предпросмотр рисует Markdown элементами React без вставки HTML, поэтому опасной разметки в шаблоне быть не может (R-3.2).

**Шкалы и конвертер** (R-2.26):

- **Шкалы.** Порядковые (майки XS–XL, свои) и числовые (очки, свои) с единицей. Системные: «Майки» (`tshirt`) и «Дни» (`days`).
- **Конвертер** — строки «значение ≈ от–до дней»; у числовой шкалы — дни на одну единицу. Строки без пространства — конвертер по умолчанию, у пространства может быть свой. «Дни» в конвертере не нуждаются.
- **Конвертер по умолчанию:** XS 0,5–1, S 1–2, M 3–5, L 6–10, XL 11–20 дней. Это предложение для старта, его правят без разработчика.
- **Расчёт** — общие функции в `packages/contracts/src/estimates.ts`: `toDays`, `fromDays`, `estimateIn`, `rollupEstimates`. Сервер и интерфейс считают одинаково.
- **Свёртка в выбранной шкале.** Если у ребёнка есть оценка в этой шкале, она берётся как есть, иначе приводится его первая оценка. Числовые шкалы суммируются в своих единицах. Порядковые — в днях, итог приводится к значению, чей диапазон ближе к середине суммы. Каждый ребёнок учитывается один раз.
- **API свёртки** — `POST /api/v1/estimates/rollup`; на нём YT-10 будет считать свёртку оценок.

**Стартовые данные** создаёт миграция `0003_ticket_types`, поэтому они есть в любой установке:

- **6 типов:** Цель, Эпик, Стори, Задача, Баг, Реквест. «Отсутствие» добавит YT-25.
- **7 полей:** исполнитель, фичекоманда, стрим, срок, размер (майки), оценка в днях, серьёзность.
- **3 шаблона** по R-2.7:
  - «Стори» — разделы «Задача», «Документы», «Цели», «Требования», «Список контента», «Шаги производства», «Критерии приёмки»;
  - «Обычная задача»;
  - «Баг» — по разделу 7 инструкции по Тайге: краткое описание, шаги воспроизведения, ожидаемый и фактический результат, материалы, связь с фичей; серьёзность «Обычный».
- **Шкалы и конвертер по умолчанию.**

Стартовые типы, шаблоны и шкалы удалить нельзя, править можно.

**Права.** Читать настройку может любой вошедший, менять — суперадмин со второй проверкой. Выдача права «админ» — YT-08. Тестовые сущности скрыты от обычных пользователей (ADR 0006).

## Последствия

- Критерий «у стори две оценки — M и 6 дней; обе видны, свёртка родителя считается в выбранной шкале» сейчас проверяется на предпросмотре шаблона и через `POST /api/v1/estimates/rollup`. На настоящих тикетах — в YT-06 и YT-10.
- Ограничитель подчинения хранится и проверяется, но применять его негде, пока нет иерархии (YT-09).
- Иконки — фиксированный набор: так тип одинаково выглядит на вебе, в мобильном клиенте и у помощника. Расширяется в `TYPE_ICONS`.
- Калибровку конвертера по фактическому времени (R-2.26) добавит YourDash, когда появится история статусов.
