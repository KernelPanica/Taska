# 0013. Неизменяемый журнал тикета и комментарии

- Статус: принято, 2026-11-17
- Требования: R-2.25 (история и комментарии), R-2.5 (сущность «Событие истории»), R-2.17 (недоступные тикеты не раскрываются), R-3.2; карточка YT-07. Смежные: YT-18 (уведомления об упоминаниях), YD-05 (метрики потока)

## Решение

**Журнал** — таблица `ticket_history`, одна запись на одно изменённое поле:

- кто: `actor_id` и имя снимком `actor_name`;
- когда;
- что: `field`, у полей типа ещё и название снимком;
- было и стало: `{ raw, text }`;
- источник: `person`, `system`, `rule` или `assistant`, с пояснением `source_detail`.

**Значения хранятся снимком.** `raw` — как сохранено, `text` — как читалось в момент изменения: имена людей, названия статусов, метки вариантов, значения шкал.

- Если человека убрали из тикета, переименовали или деактивировали, история читается как была, профиль не трогается.
- Деактивированные люди не удаляются (ADR 0009).

**Неизменяемость** обеспечена дважды:

1. В API нет действий правки и удаления журнала.
2. Триггеры `BEFORE UPDATE` и `BEFORE DELETE` в базе отклоняют любую попытку (`ticket history is append-only`).

Это проверяют тесты. Тикеты не удаляются, корзина появится в YT-14, поэтому записи журнала не осиротеют.

**Что пишется.** Сервис тикетов сравнивает тикет до и после каждого действия (`historyService.diff`) и пишет разницу в той же транзакции, что и само изменение:

- название, описание, чеклист;
- статус и исход, тип;
- приоритет, теги, даты, блокировка, причина отмены, архив;
- каждая роль людей;
- каждое поле типа.

Создание — записи «создан», «шаблон» и стартовый статус. Перенос тикетов при правке схемы статусов (ADR 0011) пишется от имени системы. Для тикетов, созданных до журнала, миграция добавила запись о текущем статусе с пометкой «history started». Источники `rule` и `assistant` готовы для конструктора правил и помощника (R-2.38, R-2.39).

**Последовательность статусов** для метрик и старения карточки — `GET /api/v1/tickets/{key}/status-history`, в JSON или CSV. Для каждого статуса отдаются вход, выход (у текущего — `null`), исход, кто перевёл, категория. Строится только из журнала, без отдельной таблицы.

**Комментарии** — таблица `ticket_comments`.

- Текст в Markdown. Показ — тот же безопасный компонент, что для описания (ADR 0012), плюс цитаты `>`.
- Править можно только свои. Удалять — свои, а суперадмин любые; профили прав — YT-08.
- Удаление мягкое: в ленте остаётся «Комментарий удалён», текст больше не отдаётся. Имя автора хранится снимком.

**Упоминания.**

- **Человек** — `@логин` из каталога YourSpace. В поле комментария есть подсказка по логину и имени.
- **Тикет** — по ключу `AOS-N`.
- Сервер сохраняет упоминания в `comment_mentions` — для уведомлений YT-18 — и при чтении отдаёт их уже разобранными для конкретного зрителя.
- Ссылкой становится только то, что распознано и видно зрителю. Недоступный тикет остаётся простым текстом, без названия (R-2.17).

**«Сделать тикетом».** Создаёт задачу в том же пространстве:

- описание начинается со ссылки на комментарий (`/tickets/AOS-7#comment-…`) и цитаты из него;
- исполнитель выбирается при создании;
- в журнале исходного тикета появляется запись «задача из комментария».

Комментарий показывает ключ задачи и её текущий статус. Из одного комментария — одна задача. Формальная связь между тикетами появится в YT-12.

## Последствия

- Журнал растёт без удаления. Индексы по тикету и по полю со временем покрывают и карточку, и выборку статусов для метрик (R-3.4 проверим нагрузочным тестом в YT-30).
- Уведомления об упоминаниях, «редактирует Имя» и обновления без перезагрузки — в YT-18 и позже.
