# 0011. Схемы статусов и исходы

- Статус: принято, 2026-11-17
- Требования: R-2.10 (статусы), R-2.7 (смена типа), R-5.1 (стартовые схемы); карточка YT-05. Применение к тикетам — YT-06 (ADR 0012)

## Контекст

Процесс каждого типа настраивается без разработчика. При этом система должна понимать, что в работе, а что завершено: от категорий зависят прогресс, свёртки, просрочка и WIP. Схема задаётся на тип внутри пространства.

## Решение

**Где живёт схема.** `status_schemes` — схема на тип. Строка с `space_id = NULL` — схема по умолчанию для всех пространств, строка с пространством — его своя схема. Так же устроен конвертер оценок (ADR 0010): схему не нужно заводить в каждом пространстве, но любое может завести свою.

- **Своя схема пространства.** При заведении тикеты этого пространства переносятся со статусов схемы по умолчанию на новые по правилу смены типа: имя → категория → первый подходящий. При возврате к схеме по умолчанию — так же обратно.

**Статус** (`scheme_statuses`) хранит:

- имя, уникальное в схеме;
- категорию: `queue` (очередь), `in_progress` (в работе) или `done` (завершён);
- признак «ожидание» (`waiting`) — статус-буфер;
- исходы — только у завершённого и минимум один, это проверяется и в коде, и `CHECK` в базе;
- обязательное на входе — `requirements`: поле типа, человек (исполнитель, заказчик, тестировщик), описание, «все пункты чеклиста отмечены»;
- ответственные роли: ГД, ПМ, исполнители, тестировщик;
- флаг «требования заморожены».

Роли и заморозка пока только хранятся. Уведомление роли — YT-18, действие «Изменить требования» — YT-07.

- **Id статуса** сохраняется при правке схемы. Убранный статус переносит свои тикеты по имени, иначе по категории.

**Исходы** — на тип (`ticket_types.outcomes`): по умолчанию «выполнено» и «отменено», у бага — «исправлено», «не исправляем», «дубль» и «отменено». «Отменено» обязательно у каждого типа. Исход, который использует статус схемы, убрать из типа нельзя.

**Правила** — чистые функции в `packages/contracts/src/workflow.ts`, общие для сервера и интерфейса и покрытые модульными тестами (`apps/api/tests/workflow.test.ts`):

- `validateScheme` — у каждого статуса есть категория; у завершённого — исход; исходы только у завершённых и только из исходов типа; имена уникальны; есть завершённый статус с исходом «отменено».
- `canTransition` — переходы свободные. С опцией «строгий порядок» можно только на следующий статус или назад на любой.
- `cancelTarget` — отмена ведёт в первый завершённый статус, где разрешено «отменено». Отмена доступна из любого статуса и не подчиняется строгому порядку.
- `missingRequirements` — что не заполнено для входа в статус.
- `mapStatusOnTypeChange` — сначала по имени без учёта регистра, иначе по категории, если подходит ровно один статус. Иначе — вопрос человеку со списком кандидатов: статусы той же категории, а если их нет — все.

**Стартовые схемы** (миграция `0004_status_schemes`) — по R-5.1: стори, баг, задача, реквест, эпик, цель. Условия входа взяты из таблицы R-5.1, в пределах того, что уже есть:

| Статус                   | Обязательно на входе                |
| ------------------------ | ----------------------------------- |
| Discovery                | исполнитель, срок                   |
| Discovery Done           | описание; требования замораживаются |
| To Do (стори)            | размер, исполнитель, дни, срок      |
| To Do (баг)              | описание (шаблон бага), исполнитель |
| Creation, Implementation | срок                                |
| Test                     | срок, тестировщик                   |
| Done (стори)             | все пункты чеклиста                 |

- «Привязка к цели или вехе» появится с иерархией (YT-09), комментарии тестировщика — с комментариями (YT-07).
- Признак «ожидание» стоит у «… Done»-статусов, как в таблице R-5.1. To Do в таблице без него, хотя текст R-2.10 называет To Do буфером. To Do — очередь и в WIP не считается при любом значении признака, поэтому следуем таблице. Админ меняет это одной галочкой.

**Поле «Исполнитель» убрано из типов:** исполнители стали встроенной частью тикета — несколько человек плюс заказчик, тестировщик и наблюдатели (YT-06). Иначе у исполнителя было бы два источника. Требование «исполнитель» в схеме — это `people: assignees`.

**Новый тип** получает простую схему Backlog → In Progress → Done.

## Последствия

- Схема меняется без разработчика; её нельзя сохранить в состоянии, где тикет нельзя отменить или где у завершённого статуса нет исхода.
- Ответственные роли, «требования заморожены», уведомления и история переходов только хранятся. Работать начнут в YT-07 и YT-18.
