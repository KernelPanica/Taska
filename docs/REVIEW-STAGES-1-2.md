# Повторная проверка этапов 1 и 2

Дата: 29 сентября 2026 года. Проверены требования разделов «Этап 1» и «Этап 2»
из [Taska-Roadmap.md](../Taska-Roadmap.md), с учётом согласованных правил PM,
доступа, назначения себе через запрос и проверки результатов работы.

## Обнаружено и исправлено

1. **Базовые типы зависели от деморежима.** Обычный проект создавался только с
   типом Task. Теперь создание проекта добавляет Task, Bug, Request, Story и Epic.
   Миграция `0007_default_issue_types` дополняет существующие проекты, сохраняя
   имеющиеся типы, цвета, иконки и ссылки из задач. Повторный запуск не создаёт дубликатов.
2. **Изменение ключа проекта меняло ID и URL всех задач.** Ключ теперь недоступен
   для редактирования после создания проекта, включая подменённый POST из админки.
   Название проекта можно менять; ссылки и ID сохраняются.
3. **Удаление задачи между валидацией и сохранением формы приводило к исключению.**
   Теперь это конфликт сохранения: задача не восстанавливается, несохранённый текст
   остаётся в форме, сервер не отвечает ошибкой 500.
4. **Подписанный администратор мог исчезать из наблюдателей при изменении участников.**
   Администратор вправе наблюдать за задачей без отдельного членства в проекте.
   Такой существующий выбор теперь сохраняется в форме PM; посторонние пользователи
   по-прежнему недоступны для назначения.

Все четыре случая закреплены регрессионными проверками. Также повторно проверены
ранее исправленные обход проверки через устаревший статус и обработка удаления
задачи во время выполнения почтовой очереди.

## Выполненные проверки

- **25 тестов приложения**: карточка, валидация, права, конфликты, участники,
  комментарии, приглашения, файлы, уведомления и регрессии.
- **3 браузерных сценария**: вход/навигация, полный цикл карточки, сотрудничество
  и проверка PM. После расширения сценария второго этапа он повторно прошёл с двумя
  исполнителями и русскими названиями статусов. Размеры: 360, 768, 1280 и 1920 px.
- **Файловая SQLite**: миграция 0006 → 0007 сохраняет настройки существующих типов;
  два потока создают 10 задач с уникальными номерами 43–52; после удаления номера 52
  следующая задача получает 53. Комментарий, отчёт и файл сохраняются после снятия
  исполнителя и переподключения. Удаление задачи очищает её файл после фиксации транзакции.
- Ruff, отсутствие расхождения моделей и миграций, проверка пробелов и полноты
  русских переводов пройдены.

Воспроизведение:

```sh

PYTHONPATH=src .venv/bin/python tests/check_persistence.py
RUN_BROWSER=1 .venv/bin/python manage.py test tests.browser --settings=taska.test_settings
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python manage.py makemigrations --check --dry-run --settings=taska.test_settings
```

Файловая проверка работает в отдельной временной базе и включена в CI.
Браузерные снимки: `artifacts/checkpoint1-issue.png`, `artifacts/checkpoint2-review.png`.

## Границы результата

Технические пункты этапов 1 и 2 проверены. Приёмка командой не отмечена за пользователя.
Реальная доставка SMTP проверяется отдельно на настроенном домене; здесь использован
тестовый почтовый адаптер. Полная неизменяемая история изменений относится к этапу 5.
Интерактивное перетаскивание Kanban относится к этапу 3 и в эту проверку не включено.
