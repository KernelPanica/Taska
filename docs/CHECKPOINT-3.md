Реализован для приёмки пользователем. Демонстрация команде ещё не проводилась.

- [x] Колонки соответствуют статусам проекта с категориями «очередь», «активный», «завершённый».
- [x] PM может быстро переименовать колонку на доске; полная настройка остаётся в «Статусах».
- [x] Перенос карточки меняет статус и сохраняет позицию; перенос на карточку вставляет перед ней, на свободное место — в конец.
- [x] Смена статуса из задачи сохраняется; задача добавляется в конец новой колонки.
- [x] Вся карточка открывает задачу; ссылки, формы и кнопки работают отдельно и не начинают перенос.
- [x] Карточки показывают ID, название, тип, исполнителей, приоритет, все теги, срок и явную отметку просрочки.
- [x] Теги и исполнители открывают фильтр текущей доски; фильтры можно сбросить.
- [x] Доступны обычные формы переноса и кнопки «Выше» / «Ниже» для клавиатуры и сенсорных экранов.
- [x] Устаревшая версия задачи или доски отклоняется с конфликтом; частичный перенос не сохраняется.
- [x] Проверяется доска со 100 карточками, ограниченным числом SQL-запросов и без горизонтального переполнения страницы на ширинах 360–1920 px.
- [x] Русский и английский интерфейс; приватность и роли этапов 1–2 сохраняются.

## Правила согласования

Назначенный участник переносит свою задачу в рабочий активный статус. Перенос
участником в «На проверке» показывает подсказку об отправке результатов.
PM/admin переносит задачи между любыми настроенными колонками без подтверждений.
Если задача покидает проверку с ожидающим отчётом, перенос в завершённый статус
принимает отчёт; перенос в другой статус возвращает работу. Сам перенос не
создаёт фиктивный отчёт. Наблюдатели не перемещают карточки.
После переноса доска обновляется фоновым запросом с текущей сессией без
перезагрузки документа; прокрутка колонок сохраняется. Профиль открывает только
отдельное нажатие на карточку или её ссылку.

В «Добавить или удалить колонки» PM управляет всеми статусами, включая стандартные.
Любую пустую колонку можно удалить без замены. Если есть задачи, требуется
замена той же категории; для ожидающих проверки сохраняется роль проверки.
Если PM удалил пустую колонку проверки, перед следующей отправкой результатов
нужно назначить эту роль другой активной колонке.

## Демонстрация спринта

1. Запустить `sh dev.sh`, войти как `demo-manager`.
2. Создать 18 задач, назначить `demo-member`, добавить теги и сроки; одной задаче
   поставить вчерашнюю дату. Проверить метаданные и фильтры на доске.
3. Перенести несколько карточек между рабочими статусами, изменить порядок
   внутри колонки. Обновить страницу: порядок должен сохраниться.
4. В другой вкладке оставить старую доску. Изменить карточку в первой вкладке,
   затем попытаться перенести её во второй: увидеть конфликт без потери изменений.
5. Под участником начать работу и отправить результат; под PM принять или
   вернуть результат. Проверить, что участник не может завершить задачу сам, а PM может перенести её без подтверждения.
6. Переименовать колонку. Повторить перенос через форму «Переместить задачу»
   и кнопки порядка на телефоне или с клавиатуры.
7. Переключить RU/EN и убедиться, что анонимный браузер получает только вход.

## Проверки и ограничения

`taska.projects.test_board` проверяет порядок, конфликты, откат, права, review,
переименование, фильтрацию и 100 карточек. `tests.browser.test_checkpoint3`
проверяет настоящий drag-and-drop, сохранение после обновления, две вкладки,
формы, фильтры, переименование, RU и адаптивность. Общие сценарии этапов 0–2
сохраняют покрытие создания, назначения, отчётов и завершения.

Результат проверки: 35 серверных тестов и 5 браузерных сценариев этапов 0–3
прошли. Ruff, проверка схемы миграций и проверка обновления SQLite также прошли.

Миграция 0008 сохраняет прежний порядок существующих задач по номеру.
`tests/check_persistence.py` проверяет обновление SQLite с 0006 до текущей схемы,
сохранение данных и параллельное создание задач.

Блокировка и версия общие для проекта: даже другой параллельный проектный
запрос может потребовать обновления доски. Это намеренный простой способ защиты
порядка. Доска загружается целиком; виртуализация пока не нужна для проверенных
100 карточек. Нативное перетаскивание ориентировано на мышь; на сенсорном экране
используются обычные формы. Связи задач относятся к этапу 4.
