# Taska Team Workspaces Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Перевести Taska на рабочие пространства команд с singleton project, полноценной Issue, глобальными шаблонами, настройками и Plugin API v2 и обновить production после локальной и Docker-проверки.

**Architecture:** Сохранить Fastify/SQLite и обязательные внутренние project FK, но перенести область авторизации и выборок на Issue.teamId и Sprint.teamId. Использовать один global workflow, общие серверные policy и Issue mutations; React-представления команд потребляют ограниченные страницы данных. Доверенные плагины загружаются раздельно на сервере и клиенте, а API v1 обслуживается адаптером.

**Tech Stack:** TypeScript, Node.js >=22.12.0 (Docker Node 24), npm workspaces, Fastify 5, Drizzle + better-sqlite3, Zod contracts, React 19, React Router 7, TanStack Query/Virtual, TypeUI Enterprise primitives, Vitest/Testing Library, Playwright/axe, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-11-12-taska-team-workspaces-design.md` — читать целиком; раздел «Уточнённые правила после builder check» уточняет предыдущие формулировки, в частности admin/lead → organization admin для глобальных настроек.

## Global Constraints

- Не создавать несколько организаций, JQL, custom-field builder, marketplace или sandbox.
- Не загружать полную доску/команду в браузер: progressive pagination и virtualization сохраняются.
- Не дублировать Issue mutations между Board/List/IssuePage/TeamPage.
- Не показывать singleton project как создаваемую сущность и не оставлять старые project filters в навигации.
- Не менять TypeUI Enterprise: dark theme, tokens, IBM Plex Sans, glass panels, Phosphor, WCAG AA.
- Не хранить секреты плагинов в client.js или передавать env в browser.
- Плагины доверенные, устанавливаются администратором файлами в `/data/plugins`; server code не отправляется в браузер.
- Один singleton project без teamId; один global workflow; один active sprint на teamId. Issue.projectId остаётся обязательным внутренним FK; Issue.teamId обязателен.
- Site Settings, global Issue templates и Board template доступны только organization admin. Team lead управляет командой и её задачами; viewer может self watch/unwatch.
- Markdown хранится текстом; renderer санитизируется на клиенте; экспорт `.md` не требует attachment.
- Performance/security: 10k Issue progressive pagination, bundle ≤200 KiB initial gzip, no full team in initial response, no client-side secret exposure, Playwright console/axe/responsive checks.
- Работать поверх существующего TypeScript monorepo; старый Python README не является описанием текущего runtime. Не откатывать уже имеющиеся изменения рабочего дерева.
- Этот документ — план, не реализация. При его исполнении staging и commits не требуются и не являются шагами или критериями готовности.
- Финальный deploy: `https://yourwiki.kernelpanica.tech`, строго после локальных, Docker и backup/restore проверок. В рамках написания плана production не менять.

## Review Focus

1. Миграция нескольких проектов с одинаковыми status keys, конфликтующими ролями и active sprints: все ссылки сохраняются, роли объединяются вверх по rank, warnings воспроизводимы; rollback не оставляет полумиграцию. Тесты Task 1.
2. Доступ после изменения иерархии/переноса Issue: нет доступа вверх и утечек через links, reports, SSE, watchers или compatibility projectId. Тесты Tasks 2–3.
3. Одновременные изменения исполнителей и статусов с устаревшей version: 409, атомарный порядок, корректный primary, одна Activity и уведомления без дублей; UI откатывает optimistic cache. Тесты Tasks 3–4.
4. Markdown с HTML, javascript/data URLs и Unicode, включая template preview/export: безопасное отображение и точное сохранение исходного текста. Тесты Task 4.
5. Ошибка/повторная загрузка плагина, смена сессии или команды: нет старого widget context, двойных listeners, обхода policy либо выдачи server.js/config secrets. Тесты Task 7 и release checks Task 8.

**Общие контракты, определяемые в Tasks 1–3:**

- `TeamRole = 'viewer' | 'member' | 'lead'`; organization role остаётся `'admin' | 'member'`.
- `CursorPage<T> = { items: T[]; nextCursor: string | null }`; `OffsetPage<T> = { items: T[]; total: number; limit: number; offset: number }`. Общие типы экспортировать из `team-workspace.ts`, убрать дубли в web api.
- `TeamSummary = {id:string;name:string;parentId:string|null}`; team people option `TeamPerson = {id:string;name:string;email:string}`.
- `TeamScope = { teamId: string; includeDescendants: boolean }`; по умолчанию `includeDescendants=true`.
- `Issue` дополняется `teamId: string`, `assigneeIds: string[]`; `assigneeId: string | null` — первый элемент или null. `Sprint` получает `teamId: string`.
- `TeamIssueQuery` расширяет текущие issue query options: `includeDescendants?: boolean`, `cursor?: string`, `limit?: number` (1..100, default 100). Сохраняются status/type/assignee/q/parentId filters; assignee ищет по join table, cursor привязан к scope+filters.
- Новые Issue API используют `assigneeIds`; compatibility принимает `assigneeId`. Одновременная передача обоих полей → 422 `AMBIGUOUS_ASSIGNEES`; отсутствие обоих при update не меняет список. Повторяющийся userId в новом массиве → 422 `DUPLICATE_ASSIGNEE`.
- Ошибки предметной области возвращают `{ code: string; error: string }`; 401 session, 403 permission, 409 version/conflict, 422 input/migration. Существующие не связанные endpoint-контракты не менять.
