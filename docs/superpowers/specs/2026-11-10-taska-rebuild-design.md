# Taska Rebuild Design

## Назначение

Taska — self-hosted таск-трекер для одной организации с командами и вложенными подкомандами. Первая версия объединяет основной рабочий процесс Taiga и базовую Jira: проекты, эпики, истории, задачи, подзадачи, Kanban, backlog, спринты, настраиваемые workflow, шаблоны, совместную работу, роли, история и уведомления.

Продукт должен быть удобен как Kaiten, визуально использовать TypeUI Enterprise, быстро загружаться, потреблять минимум ресурсов и развёртываться одной командой. Общие действия реализуются один раз и используются всеми представлениями. Возможности расширяются плагинами без изменения ядра.

## Цели

- Единая модель Issue для Epic, Story, Task, Bug и Subtask.
- Команды неограниченной вложенности, проекты и централизованные разрешения.
- Kanban, список, backlog, спринты, эпики, Story Points, WIP-лимиты, Burndown и Velocity.
- Шаблоны задают тип, обязательные стандартные поля, значения по умолчанию, Markdown-описание, чек-листы, workflow и layout страницы.
- Комментарии, вложения, наблюдатели, теги, Activity и внутренние уведомления.
- REST API `/api/v1`, OpenAPI и SSE для синхронизации представлений.
- SDK доверенных однофайловых плагинов и эталонный GitHub OAuth.
- Docker Compose с одним контейнером и SQLite volume; миграции и backup/restore.

## Не цели

- Несколько организаций на одной установке.
- JQL, произвольные пользовательские поля, сложная автоматизация и внешняя BI.
- Микросервисы, Redis, отдельный worker, PostgreSQL и горизонтальное масштабирование ядра.
- Перенос старого Python-кода и миграция данных MVP.
- Marketplace, sandbox или установка непроверенных плагинов.
- Произвольные React-компоненты в однофайловых плагинах первой версии.

## Ограничения и анти-цели

- TypeScript strict, Fastify, React и SQLite обязательны.
- Один Node-процесс и один контейнер; никаких обязательных внешних сервисов.
- Низкая задержка и компактный frontend важнее декоративной сложности.
- Нельзя создавать отдельные реализации изменения статуса, назначения или шаблонов для разных страниц.
- TypeUI Enterprise обязателен: dark theme, modular grid, glass-like panels, subtle gradients, soft shadows и strong data hierarchy.
- WCAG 2.2 AA, keyboard-first, reduced motion и адаптивность обязательны.
- Нельзя загружать весь проект или все Issue в браузер для построения представлений.
- Плагины доверенные и имеют права кода сервера; их устанавливает владелец установки.

## Подходы

### Выбран: модульный монолит

Fastify обслуживает API и production-сборку React. Модули организации, команд, проектов, Issue, workflow, шаблонов, совместной работы и авторизации разделены по ответственности, но работают в одном процессе. SQLite выбран вместе с Compose: один контейнер Taska и постоянный volume `/data`.

Этот подход выбран пользователем ради минимального потребления ресурсов, быстрой установки и простой эксплуатации.

### Отклонён: раздельные сервисы и процессы плагинов

Изоляция и независимое масштабирование сильнее, но межпроцессные вызовы, очередь и эксплуатация нескольких сервисов противоречат выбранным простоте и SQLite. SDK не должен блокировать такое развитие в будущем.

## Архитектурные решения

### Структура

npm workspaces: `apps/api`, `apps/web`, `packages/contracts`, `packages/plugin-sdk`. В `contracts` находятся общие Zod-схемы и типы API. В `plugin-sdk` — стабильный версионируемый контракт расширений. Клиентские и серверные модули не дублируют бизнес-правила.

### Данные и сервер

`better-sqlite3` и Drizzle ORM; WAL, foreign keys, транзакции, миграции при старте, явные индексы и пагинация. Вложения и плагины хранятся в `/data`, в БД остаются метаданные. Пароли обрабатываются Node `scrypt`; сессии — HttpOnly/SameSite cookie; изменяющие запросы защищены от CSRF. Логин ограничен по частоте попыток.

### Права

Роли организации: `admin`, `member`. Роли команды и проекта: `lead`, `member`, `viewer`.

- Org admin имеет полный доступ; org member сам по себе не открывает проекты.
- Роль родительской команды наследуется вниз; роль подкоманды не открывает родительскую.
- Прямая проектная роль добавляет или повышает доступ; effective role — наиболее широкая из унаследованной и прямой, без deny.
- Viewer читает; member создаёт и редактирует Issue, комментирует и выполняет разрешённые переходы; lead дополнительно управляет проектом, шаблонами, workflow и спринтами.
- Один policy-модуль обязателен для всех API.

### Issue и шаблоны

Иерархия: Epic → Story/Task/Bug → Subtask. Subtask не имеет детей. Другие parent-child связи и связи между проектами запрещены. `blocks`, `relates_to`, `duplicates` хранятся отдельно.

Единый IssueService транзакционно выполняет создание, редактирование, переходы, назначение, перемещение в спринт и смену иерархии. Activity записывается в той же транзакции. Уведомления создаются из событий после commit.

TemplateService проверяет тип, обязательные стандартные поля, чек-листы, defaults, workflow и схему блоков. TemplateRenderer используется для просмотра и редактирования. Встроены Epic/Story/Task/Bug/Subtask.

### Workflow и доски

Проект имеет default workflow; шаблон может ссылаться на другой workflow того же проекта. Статусы имеют категорию `todo/in_progress/done`, порядок и WIP-лимит. Kanban показывает объединение статусов; переход разрешён только конкретным workflow Issue. Причина запрета доступна через API и UI.

### Спринты и отчёты

Спринт принадлежит проекту. Issue находится максимум в одном спринте. Разрешено много planned и только один active на проект. Burndown использует оставшиеся Story Points и ежедневные snapshots, учитывая изменения состава. Velocity — завершённые Story Points каждого завершённого спринта.

### Пользователи и OAuth

Первичный setup однократно создаёт администратора. Далее используются одноразовые копируемые ссылки-приглашения; SMTP не требуется. Публичной регистрации нет. GitHub OAuth завершает регистрацию только с действующим приглашением. Привязка к существующему аккаунту происходит после входа. Автоматической привязки по email нет.

### Плагины

ESM-файл экспортирует manifest (`id`, `version`, `apiVersion`, capabilities) и `register(context)`. SDK поддерживает auth-provider, API routes, подписки на доменные события, декларативную навигацию и настройки. Ядро само рисует кнопки auth-provider.

Плагины загружаются из `/data/plugins` при старте. Ошибка или несовместимая версия не роняет ядро и отображается администратору. Секреты задаются через env/защищённые настройки. Эталонный сценарий: скопировать `github-auth.js`, задать client id/secret, перезапустить и увидеть вход через GitHub.

### Интерфейс

TypeUI Enterprise токены: primary `#0C5CAB`, secondary `#0A4A8A`, success `#10B981`, warning `#F59E0B`, danger `#EF4444`, surface `#09090B`, text `#FAFAFA`; IBM Plex Sans; типографика 12/14/16/20/24/32; radius 4/8 px; сетка 8 px.

Общие компоненты имеют default/hover/focus/active/disabled/loading/error состояния. Phosphor — единственное семейство иконок; emoji не используются как controls. Glass и градиенты не снижают контраст и производительность. Текст имеет контраст минимум 4.5:1. Drag-and-drop имеет клавиатурную альтернативу. Проверяются 375/768/1024/1440 px и reduced motion.

Страницы: setup/login, «Моя работа», проекты, команда, уведомления, настройки; проект содержит Kanban, список, backlog/sprints, эпики и отчёты. Страница Issue строится TemplateRenderer. Markdown используется вместо тяжёлого WYSIWYG. Длинные списки виртуализируются, маршруты lazy-loaded, фильтры хранятся в URL, optimistic updates откатываются при ошибке.

### Эксплуатация

Многоступенчатый Dockerfile на Node LTS, non-root, Fastify static с immutable cache и сжатием. Compose содержит один сервис и volume. Quick start генерирует секреты Node-контейнером. Backup/restore использует SQLite online backup. Обновления не требуют пересоздания БД.

## Критерии приёмки

- Пройдены lint, strict typecheck, unit/integration/component/E2E и production build.
- E2E покрывает setup → приглашение → подкоманда → проект → Issue по шаблону → Kanban/backlog/sprint → комментарий/уведомление.
- Отдельный E2E доказывает установку GitHub-плагина.
- Production Compose сохраняет данные после перезапуска; backup → изменение → restore работает.
- Повреждённый/несовместимый плагин не мешает запуску ядра.
- Нет console errors; выполнены accessibility и responsive проверки.
- Initial JS не более 200 KiB gzip; Lighthouse desktop performance минимум 90 на основных production-страницах.
- API и доска проверены минимум на 10 000 Issue.
